# Warren review, 2026-10-14

A full pass over the code and the running app. I built the web app, ran the typecheck and the test suite (59 files, 537 tests, all green), started a fresh hub on a scratch data folder, connected this Mac as a real device, and clicked through every page on desktop, phone width, light and dark. Three code reviewers (hub, web app, node/packages) read every source file; I spot-checked their strongest claims against the code and marked which ones I confirmed myself.

Legend: **P0** security or data loss · **P1** a feature doesn't work · **P2** a rough edge people will hit · **P3** polish.

## What works well

- First-run setup, the five-step **Get started** flow, device connection (the daemon connected in seconds and the page updated by itself), agent discovery (it found the Claude Code and Hermes setups on this Mac), creating agents from the side panel, job templates.
- A real agent run end to end on Codex: @mention → 👀 reaction → streamed "thinking / using chat_react" status → reply → note written to the vault → reaction added. Threads, DMs, reactions, ⌘K search (messages and notes both found), the Tools-used disclosure.
- Memory: notes, folders, edit/preview, wikilinks, the share dialog, graph, activity, "view as" an agent.
- Teams: create, drag/+ onto the chart, lead detection, roles, Work and Settings tabs, the team channel.
- Connectors catalog and Add dialog, skills shop and install (the skill landed in the agent's folder), About you, every Settings page, the Orchestration addon checklist, New task → dispatcher → subtask.
- Phone layout: bottom tab bar, full-screen pages, no horizontal overflow on any page I checked. Light and dark both clean. Copy is friendly and explains itself.

## Things I saw break while testing

1. **P1 · A connector that can't start fails silently.** I added the Time connector to Nova. It needs `uv`, which this Mac doesn't have. The Add dialog shows "Needs: uv on the device" as a note but still lets you connect, nothing checks the device, and when Nova ran, Codex just fell back to its own built-in tool and said "I called web.run's Time tool". Nothing told me the connector never started. Fix: ask the device whether the command exists before enabling (the daemon already reports harnesses this way), and surface "connector X didn't start" in the run.
   **Fixed:** the device now reports which commands connectors need are on its PATH (`capabilities.commands`, from the catalog plus node/npx/uv/uvx/docker). The Add dialog checks each chosen agent's device and warns "Nova's device my-mac doesn't have \"uvx\"" before you press Connect (you can still connect; it works once the command is there), and the API answers with the same `warnings`. When a run starts, a connector whose command is missing is left out and a notice "Connector time didn't start: \"uvx\" isn't installed on my-mac." is logged on the device and kept with the agent's reply. Tests: hub.test.ts "connector prerequisites", node.test.ts "says when a connector didn't start".
2. **P1 · A harness that needs a sign-in shows a raw API error.** Atlas (Claude Code) replied "Run failed: Failed to authenticate. API Error: 401 OAuth access token has expired. Re-authenticate to continue." That's the expired Claude login on this Mac, not Warren, but a non-technical person has no idea what to do. Translate known sign-in errors into "Claude Code on my-mac needs to be signed in again. In Terminal there, run `claude` and then `/login`." with a link to the agent's page, and show the same hint on the agent's Overview while it's broken. (The Get started page also kept saying "Atlas is ready to work" under the failure.)
   **Fixed:** `signInProblem` in packages/core recognises the sign-in errors of Claude Code, Codex and the other harnesses with a login command, and the hub posts "Run failed: Claude Code on my-mac needs to be signed in again. In a terminal there, run `claude (then /login)`; then ask again." instead of the raw error. The agent's runs carry a `hint`, and the Overview shows a warning box with it while the latest run failed that way. The raw error stays on the run for the Runs page. Tests: core.test.ts "signInProblem", hub.test.ts "explains a harness that needs signing in". (The Get started copy is untouched.)
3. **P1 · A task whose agent run fails stays "Working" forever.** With Orchestration on, Nova (dispatcher) handed a subtask to Atlas. Atlas's run failed within seconds (the sign-in error above), but the subtask and the parent task both still say "Working" on the Tasks page minutes later, with no failure, no "Waiting on you", and nothing in the task for the dispatcher to react to. A failed run should fail (or hand back) the task, and the dispatcher should be told.
   **Fixed:** when a run fails, the task it was working on fails with the reason as its result, and a message in the task's thread says so; if an agent handed the task out (the dispatcher, a lead) it's @mentioned, so it wakes up and can hand the work out again (`failTaskOfRun` in orchestration.ts). A person's task says to fix the cause and reopen it on the Tasks page. Test: hub.test.ts "fails the task a failed run was working on".
4. **P2 · The note header in Memory truncates to a few letters** even with plenty of room: "Proje › Launch · edited by Y…" at 1024px, "Ag‹ @n‹ stren" on a phone. [VaultView.tsx:421-425](apps/web/src/views/VaultView.tsx:421) nests `truncate` flex items so every crumb shrinks.
5. **P2 · DM composer breaks when the thread panel is open.** With a thread open in a DM, the composer toolbar ("Can edit files", model, effort) wraps into three lines and overlaps the "Message Nova" placeholder. Needs a breakpoint or a collapsed toolbar below ~600px of composer width.
6. **P2 · "New task" sits at the top of the sidebar even when Tasks is off.** Clicking it opens a dialog that only says "Tasks is an addon". Either hide the entry until Orchestration is on, or make it the plain "hand this to an agent" flow. [Sidebar.tsx:110](apps/web/src/components/Sidebar.tsx:110)
7. **P2 · Two different stories about how to get VMs.** Get started step 2 says "Apple's container is installed but not running: run `container system start`" and offers `warren setup`; the Computers → Add computer dialog on the same workspace says "None of your devices can run VMs yet: install Docker on one." [ComputersView.tsx:191](apps/web/src/views/ComputersView.tsx:191) should use the device's own capability text like Welcome does.
8. **P3 · Devices page contradicts itself.** The card shows "online" and "last seen 3m ago" at the same time ([NodesView.tsx:81](apps/web/src/views/NodesView.tsx:81)), and says "Its own screen is off. Agents use VMs instead." on a device set to run agents headless.
9. **P3 · Channel settings "Members · 1"** counts people only, while the tab lists one person and one agent. [Channels.tsx:231](apps/web/src/components/Channels.tsx:231)
10. **P3 · "Get started" in the channel header reopens finished onboarding** at step 5 and lets you re-send the first task. [ChannelView.tsx:527](apps/web/src/views/ChannelView.tsx:527)
11. **P3 · Data & export squeezes the "Where" label** to one word per line because the long data path doesn't wrap until the row has shrunk. [workspace.tsx:785](apps/web/src/views/settings/workspace.tsx:785)
12. **P3 · Team chart cards aren't reachable by keyboard or screen reader** (no button role; "Click to add a role" is a div). Same for the Welcome job cards.
13. **P3 · Dashboard says "1 agents"**, and the first-run setup form is left-aligned in an otherwise empty page; centering it like the Get started steps would feel finished.
14. **P3 · Wikilinks by title don't resolve.** `[[Nova's strengths]]` renders as a link but goes nowhere and draws no graph edge (the file is `strengths.md`). Either resolve titles or style unresolved links differently, as Obsidian does.
15. Note, not a bug: replying in a thread under an agent's message wakes that agent without an @mention. Reasonable, but it costs a run; worth a hint in the composer ("Nova will answer").

## Hub (server) findings from the code review

Confirmed by me where marked ✔.

- **P0 ✔ Every DM, agent stream and reaction is broadcast to every browser in the workspace.** [hub.ts:113-115](apps/hub/src/hub.ts:113) has an `only` filter but [hub.ts:327](apps/hub/src/hub.ts:327), `:266`, `:401`, `:432` never use it. REST hides DMs; the WebSocket doesn't. The web client only drops what it doesn't recognize, so anyone with DevTools can read everyone's private conversations with agents. This matters the moment you invite a second person.
   **Fixed:** `hub.audience(channelId)` gives the `only` filter for a channel (everyone for a channel; a DM's members and the workspace owners for a DM, the rule REST uses), and every `message`, `run_event`, `reactions`, system notice and `approval` broadcast passes it. Test: hub.test.ts "never sends a DM, its run events or its reactions to someone else's socket".
- **P0 ✔ `GET /api/agents/:id/runs` leaks DM text to any user, including guests.** [api.ts:571-578](apps/hub/src/api.ts:571) returns the first 280 characters of every triggering message with no channel visibility check.
   **Fixed:** runs in a channel the caller can't see keep their status and timing but have `trigger` and `channelName` blanked. Test: hub.test.ts "hides what was said in a DM from an agent's run list".
- **P0 ✔ Approvals are visible to and decidable by everyone.** [api-computers.ts:422-427](apps/hub/src/api-computers.ts:422) returns every approval in the workspace to any user, including ones raised in a DM they can't see.
   **Fixed:** listing, reading and deciding an approval all require seeing the channel it was asked in (404 otherwise), and the `approval` event only goes to those people. Test: computers.test.ts "keeps an approval between the people in the conversation it was asked in".
- **P1 ✔ Removing a member doesn't disconnect their device.** [api-settings.ts:145](apps/hub/src/api-settings.ts:145) revokes tokens by `created_by`, but node tokens are created with no creator, so the device stays connected and its agents keep running; the deleted user's id stays as the device owner so nobody can edit those agents any more.
   **Fixed:** removing someone also revokes the tokens of every device they own and the harness tokens of the agents on them, marks those devices as owned by nobody (they stay listed, offline, until an owner removes them), and closes their device and browser sockets with code 4401, which the daemon treats as final. Test: settings.test.ts "…and disconnects what they connected".
- **P1 ✔ A failed prompt build leaves the agent "thinking" forever.** [hub.ts:422](apps/hub/src/hub.ts:422) marks the run failed silently: no status broadcast, no message, the 👀 stays.
   **Fixed:** the run goes through the same `finishRun` path as a failure reported by the device: a "Run failed: couldn't prepare the request: …" message, the agent's status back to online, and its task failed. Test: hub.test.ts "says so when a prompt can't even be built".
- **P1 · Guests can wake agents.** `POST /api/tasks`, `PATCH /api/tasks/:id`, `POST /api/channels` and `POST /api/runs/:id/cancel` use bare `need()`; the cancel route doesn't even check the workspace.
   **Fixed:** tasks and channels need `notGuest` (people who aren't guests, and agents, which act for a member; `member: true` would have locked agents out of `task_delegate`), cancel needs `member: true` and 404s for a run outside the caller's workspace. Test: hub.test.ts "lets guests look but not give agents work".
- **P1 · Queued runs pile up for an agent with no device and all fire at once when a device connects** ([hub.ts:374-378](apps/hub/src/hub.ts:374), `:212`). No cap or expiry.
- **P1 · Deleting an agent skips the device-owner check, doesn't cancel its runs, and cascades away every task ever assigned to it** ([api.ts:720-729](apps/hub/src/api.ts:720), [db.ts:66](apps/hub/src/db.ts:66)).
   **Fixed:** DELETE applies the same device-owner rule as PATCH (403 for anyone but the owner of the device it runs on), cancels its queued and running runs, fails its unfinished tasks with "@handle was removed before finishing this", and finished tasks stay with `toAgentId` null: the `tasks` table is rebuilt once (`migrateTaskAssignee`) so `to_agent_id` is nullable with ON DELETE SET NULL. Tests: hub.test.ts "keeps an agent's finished tasks when it's removed", "rebuilds the tasks table", "only lets the agent's device owner remove an agent on that device".
- **P2** `GET /api/files?channel=` lists files from channels the caller can't see ([api.ts:1655](apps/hub/src/api.ts:1655)). `?limit=abc` on messages and vault search, and a bad `x-filename` header, turn into 500s ([api.ts:602](apps/hub/src/api.ts:602), `:1357`, `:1642`). The Orgo VNC password is handed to every member's browser ([api-computers.ts:294](apps/hub/src/api-computers.ts:294)) although the code says it stays on the hub. A discussion with an offline participant never finishes ([discussions.ts:37](apps/hub/src/discussions.ts:37)). A late `run_done` after cancel flips the run back to done ([hub.ts:272](apps/hub/src/hub.ts:272)).
   **Fixed:** (files only) `GET /api/files` checks `channelVisible` for `?channel=` (404) and leaves out files shared in channels the caller can't see. Test: hub.test.ts "hides what was said in a DM … and the DM's files". The rest of this line is untouched.
- Solid: vault path handling (no traversal found), token hashing and login rate limiting, secret masking on connectors, first-run setup, every web route exists on the hub with a matching body.

## Device, installers and adapters from the code review

- **P1 ✔ A run's result is lost if the socket isn't open when it finishes.** [daemon.ts:200-202](apps/node/src/daemon.ts:200) drops the message silently; the hub only redispatches `queued` runs, so the agent stays "busy" forever after a Wi-Fi blip or a hub restart mid-run. Ctrl-C does the same ([cli.ts:116-120](apps/node/src/cli.ts:116)).
   **Fixed:** `run_done` and `run_failed` that can't be sent go into an outbox (in memory, last 200) and are sent right after the next `hello`; `daemon.stop()` now cancels runs and waits up to 5 s for each to report before hanging up, and `warren node start` awaits it on SIGINT/SIGTERM (a second signal exits at once). Tests: node.test.ts "keeps a run's result for the hub when the connection drops", "waits for runs in flight to report before stopping".
- **P1 ✔ Windows can't run npm-installed harnesses.** [process.ts:23](packages/adapters/src/process.ts:23), [acp.ts:272](packages/adapters/src/acp.ts:272) and `warren doctor` spawn without a shell, so `claude.cmd` / `codex.cmd` are never found; `warren setup` says they're installed, runs fail with ENOENT.
   **Fixed:** `spawnCommand` in process.ts starts every harness; on Windows, when the command resolves to a `.cmd`/`.bat` shim on PATH, it goes through `cmd.exe /d /s /c` with each argument quoted the way cross-spawn does (so the JSON in `--mcp-config` and Codex's `-c` values survive; plain `shell: true` would have broken them). `commandVersion`, Codex's `debug models` and `warren doctor` use the shell on Windows (their arguments are plain). Test: adapters.test.ts "windows command lines". Not run on a real Windows machine here.
- **P1 ✔ No `.gitattributes`.** On Windows the VM recipe is checked out with CRLF, so its hash never matches the published image and the local build ships shell scripts with `\r` that can't start. One line fixes it: `* text=auto eol=lf`.
   **Fixed:** added `.gitattributes` with `* text=auto eol=lf` (no tracked file had CRLF, so nothing renormalised).
- **P1 · `warren node pause` doesn't stop runs already queued** ([daemon.ts:283-287](apps/node/src/daemon.ts:283)).
   **Fixed:** a run that was waiting its turn behind another checks `paused` again when it's about to start and fails with "box is paused" instead of running. Test: node.test.ts "pausing the device also stops runs that were still waiting their turn".
- **P2** Two daemons with the same token evict each other forever (running `warren node start` while the service is installed does this; the help text invites it). A hub URL without `http://` crashes the daemon on every restart ([daemon.ts:162](apps/node/src/daemon.ts:162)). Any first-attempt failure re-runs the whole prompt from scratch ([daemon.ts:392-401](apps/node/src/daemon.ts:392)). Agent tokens and connector secrets are on the command line, visible in `ps` ([claude-code.ts:33](packages/adapters/src/claude-code.ts:33), [codex.ts:25](packages/adapters/src/codex.ts:25)). A transient token error hands the harness the device token ([daemon.ts:494-501](apps/node/src/daemon.ts:494)). Cancel only sends SIGTERM, never SIGKILL. Windows typing of non-ASCII text is garbled ([windows.ts:95](apps/node/src/computers/windows.ts:95)). `install.ps1` can stop before connecting when no VM engine is found. `install.sh` with a bare `--hub` as the last argument dies with "unbound variable".
   **Fixed:** (Windows typing and install.ps1 only) the PowerShell helper sets UTF-8 input and output encoding and is written with a BOM, so non-ASCII text typed on a Windows screen arrives intact; `install.ps1` runs `warren setup` with errors silenced and clears `$LASTEXITCODE`, so its advice can't stop the install before the device connects (like `|| true` in install.sh). The rest of this line is untouched.
- Solid: vault paths and FTS, access-rule precedence (matches the README), loop guard and mentions, the update/keeper flow, bin scripts, Docker images, protocol validation, git worktree handling.

## Suggested order

1. Privacy on the WebSocket and the three leaking endpoints (DM broadcast, agent runs, approvals), plus guest checks. Do this before inviting anyone.
2. Runs and tasks that get stuck: a failed run should fail its task and tell the dispatcher; daemon outbox/retry for `run_done`; the silent `buildPrompt` failure; pause; SIGKILL after SIGTERM.
3. Windows: shell spawn, `.gitattributes`, PowerShell encoding, `install.ps1` exit code.
4. The two "why doesn't my agent work" moments: translate harness sign-in errors, and check/report connector prerequisites.
5. Phone touch actions on messages, unsaved-note guard, attachments on failed send, the Memory header, the DM composer with a thread open.
6. The copy and consistency items (New task when Tasks is off, VM guidance, Devices card, member counts, dashboard grammar).
